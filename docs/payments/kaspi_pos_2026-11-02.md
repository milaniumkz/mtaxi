# Подключение кассы Kaspi Pay в MTaxi

Основа протокола: https://github.com/tapter-dev/kaspi-pos-automation , закреплённый commit `9b0000d38716a7c4b36867a5642a4768a3a4552f`, лицензия MIT сохранена в `server/src/kaspi_pos/LICENSE`. Это сторонняя автоматизация мобильного протокола, не подтверждение официального партнёрского API или гарантии совместимости с Kaspi. Версия Kaspi Pay 26.1029 сверена с публичной карточкой https://apps.apple.com/kz/app/kaspi-pay/id1262997215 на 02.11.2026; build 1128 взят из закреплённого upstream, не подтверждается публичной карточкой. При банковских ограничениях/изменении протокола автоматизация может не работать; штатные дополнительные проверки не обходятся.

## Как войти

1. Откройте https://mtaxi-controls.89.126.192.185.sslip.io/ под администратором MTaxi.
2. На главной раскройте «Касса Kaspi Pay».
3. Укажите номер **кассира Kaspi Pay**, имеющего права на нужную организацию; это не обязательно номер поддержки MTaxi и не произвольный номер Kaspi.kz.
4. Нажмите «Получить SMS для входа». Сервис может зарегистрировать отдельное устройство. Введите полученный код в эту форму, не в чат.
5. После подтверждения проверьте организацию. Для выставления счетов её ИИН/БИН должен совпадать с настроенным оператором MTaxi: 970905350621. Если банк возвращает несколько поддерживаемых организаций, выберите нужную.
6. Нажмите «Проверить соединение без счёта». Эта проверка читает доступность банковской сессии и не создаёт счёт/перевод.

Сам факт заполнения формы или HTTP 200 не считается входом: нужны банковские token/ключ согласования и подтверждённый профиль организации. Поле connected означает наличие полученной сессии; connectionActive подтверждается отдельной банковской проверкой. Неподдерживаемые шаги/ошибка версии/биометрическое подтверждение должны завершаться понятной ошибкой, а не фиктивным успешным входом.

## Счёт и зачисление

- Клиент создаёт обычную заявку на пополнение. Самостоятельная регистрация пассажиров/водителей остаётся по паролю; SMS здесь относится только ко входу кассира в Kaspi.
- В админке откройте заявку. «Выставить счёт через Kaspi Pay» требует отдельного подтверждения с суммой и номером из заявки. Сервер берёт их из БД, а не из произвольного тела запроса клиента.
- Перед созданием проверяются банковская сессия, организация, сумма и номер. Попытка фиксируется в БД **до** внешней финансовой операции. Повторное/одновременное нажатие не создаёт второй счёт.
- Если результат внешнего запроса неизвестен, заявка получает unknown и повтор блокируется, в том числе после перезапуска. Это требует разбора по истории Kaspi Pay; «сбросить и попробовать ещё раз» нельзя считать безопасным исправлением.
- После оплаты нажмите «Проверить оплату в Kaspi». Проверяется номер операции, организация, сумма и телефон; неизвестный статус не приравнивается к оплате. Только `Processed` считается оплаченной операцией. Ошибка/несовпадение инвалидирует прежнее положительное состояние.
- Проверка **не зачисляет деньги автоматически**. После свежего подтверждения оплаты (до 2 минут) администратор отдельно нажимает «Подтвердить оплату». Повторное подтверждение не создаёт новую проводку; одна операция банка не может зачисляться по двум заявкам.
- Отмена счёта и возвраты пока выполняются в штатном Kaspi Pay. После отмены проверьте статус здесь; до подтверждённого отказа/отмены/истечения нельзя просто отклонить связанную заявку. Неподтверждённые операции разбираются вручную без автоматического повторного выставления.
- Прежняя ручная схема сохраняется для заявок, по которым адаптер не создавал счёт: выставление в Kaspi вручную, отметка «Счёт выставлен», подтверждение администратором после сверки.

## Сервер и секреты

Новый адаптер встроен в существующий backend; отдельного публичного demo-сервера нет. Все восемь `adminKaspiPos*` callable методов требуют действительного MTaxi admin token. Для заблокированного/обычного пользователя доступа нет. Браузеру не возвращаются tokenSN, банковские cookies, приватные ключи или секрет подписи.

- `MTAXI_KASPI_POS_ENABLED`: включение адаптера; по умолчанию false, при первичной VPS-настройке включается, если параметр ещё не установлен.
- `MTAXI_KASPI_POS_KEY_FILE`: путь к независимому 32-байтовому AES-ключу (64 hex-символа в файле). Production: `/run/secrets/kaspi-pos.key`, host `/etc/mtaxi/kaspi-pos.key`, права 0600.
- `MTAXI_KASPI_POS_STATE_DIR`: production `/var/lib/mtaxi/kaspi-pos`, host тот же путь, 0700. `session.enc` — AES-256-GCM, 0600, атомарная запись.
- `MTAXI_KASPI_POS_EXPECTED_IIN`: ожидаемый получатель; пустое/несовпадающее значение блокирует счета.
- `MTAXI_KASPI_POS_APP_VERSION`, `MTAXI_KASPI_POS_APP_BUILD`: параметры текущего поддерживаемого клиента. Не угадывать/перебирать параметры для обхода ограничений; при OldVersionToUpdate нужны подтверждённые актуальные параметры/совместимость.

`deploy/setup_kaspi_pos.sh` создаёт ключ только при его отсутствии, не печатает и не перезаписывает существующий ключ, сохраняет резервную копию серверного env и готовит приватный каталог. Ключ монтируется read-only, состояние переживает пересоздание контейнера. Обычный бэкап БД не является бэкапом банковского ключа/сессии: для их восстановления нужен защищённый отдельный процесс либо новый вход через Kaspi. Удаление/ротация ключа без плана восстановления лишает доступа к текущему состоянию.

SMS-код не хранится в БД/браузерных настройках/логах; временная попытка привязана к администратору, живёт до 5 минут и ограничена пятью проверками. Новый SMS-запрос — не чаще раза в минуту. Logout удаляет локальную банковскую сессию, **не подтверждает отзыв устройства на стороне Kaspi**; устройство отзывается штатно в Kaspi Pay.

HTTP-логи не содержат тела запросов. Исходные raw-логи upstream не перенесены. Банковские запросы ограничены фиксированными HTTPS-хостами entrance-pay.kaspi.kz, mtoken.kaspi.kz и qrpay.kaspi.kz, redirect отключён, тело ограничено, timeout 12 секунд. TLS и настроенный proxy/CA сохраняются. Не вводите банковские ключи/пароли в Git, отчёты или чат.

## Проверка и ограничения

Backend-тесты с fixtures проверяют роли, привязку SMS-попытки, отсутствие секретов в ответах/БД, защищённое хранилище, однократное выставление/зачисление, неопределённый сетевой результат, неправильные организацию/телефон/сумму/операцию и отказ сессии до создания счёта. Flutter-тесты проверяют форму и отсутствие финансовой операции при входе/проверке, очистку OTP и отдельное подтверждение отправки счёта.

До ввода кассиром реального SMS в админке реальный вход, права кассира и создание/оплата настоящего счёта **не подтверждены**. Автоматические тесты не заменяют банковскую проверку. В этой задаче кассирские реквизиты не предполагались по номеру поддержки, реальные счета/возвраты без действия администратора не создавались. APK не собирается.
